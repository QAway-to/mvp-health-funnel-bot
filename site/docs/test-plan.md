# План тестов и метрик

Пункт П2 плана. Документ отвечает на три вопроса: что меряем, что считается
успехом и провалом, и какой тест имеет смысл запускать при нашем размере
трафика.

Главный вывод вперёд: **A/B-тест на покупке нам пока не по карману**, и это не
оценка на глаз — расчёт ниже. Тестировать надо середину воронки, а покупку
просто считать.

---

## 1. Что уже меряется

Бот пишет каждый шаг в PostgreSQL. Таблицы создаются сами, накатывать миграции
не нужно. Событий 26, и это не планы — они в коде:

| Шаг воронки | События |
| --- | --- |
| Пришёл | `start` (с `bucket` и `source`) |
| Взял подарок | `gift_sent` |
| Пошёл по темам | `topic_clicked`, `choice_clicked`, `choice_other` |
| Получил ролик | `video_sent`, `video_locked_shown` |
| Пошёл по курсу | `step_sent`, `course_finished` |
| Увидел предложение | `cta_shown`, `offer_clicked`, `offer_details_shown`, `plan_clicked` |
| Платит | `pay_way_chosen`, `invoice_created`, `invoice_sent`, `returned_from_checkout`, `premium_granted` |
| После покупки | `review_asked`, `review_left`, `review_consent`, `upsell_shown` |
| Замолчал | `followup_sent`, `followup_blocked` |
| Прочее | `email_already_claimed`, `price_talk_blocked` (модель полезла в цены и её остановили) |

Плюс на каждом человеке: `bucket` (A или B, деление 50/50 по хешу `chat_id` —
стабильное между перезапусками), `source` (метка источника из ссылки),
`is_premium`, `messages`, `cta_shown`, `course`, `step`, `followups_sent`,
`email`.

**Что это значит:** считать воронку можно уже сегодня, без доработок.
Единственное, чего нет, — сквозной связи с рекламой: `source` приходит из
ссылки, но Telegram Ads не возвращает нам, какой именно показ дал переход.
Поэтому стоимость подписчика считается делением бюджета на число `start` с
нужной меткой, а не по каждому клику.

## 2. Метрики: формула и запрос

### Доходимость по шагам

```sql
WITH people AS (SELECT count(*) AS n FROM funnel_users)
SELECT event,
       count(DISTINCT chat_id)                                 AS людей,
       round(100.0 * count(DISTINCT chat_id) / (SELECT n FROM people), 1) AS "% от всех"
FROM funnel_events
WHERE event IN ('start','gift_sent','topic_clicked','video_sent','step_sent',
                'cta_shown','offer_clicked','offer_details_shown','plan_clicked',
                'invoice_sent','premium_granted')
GROUP BY event ORDER BY людей DESC;
```

Это главный отчёт. Самое узкое место в нём и есть то, что надо чинить, —
а не то, что кажется узким.

### Окупаемость сегмента лендинга

```sql
SELECT source,
       count(*)                                    AS всего,
       count(*) FILTER (WHERE is_premium)          AS оплатили,
       round(100.0 * count(*) FILTER (WHERE is_premium) / count(*), 1) AS "конверсия %"
FROM funnel_users
GROUP BY source ORDER BY всего DESC;
```

Отвечает на вопрос, какую страницу стоит продвигать: `komfort` (боль в коленях)
или `sila` (силовые), или конкретное направление.

### Сравнение сценариев A против B

```sql
SELECT bucket,
       count(*)                                    AS людей,
       count(*) FILTER (WHERE is_premium)          AS оплатили,
       round(avg(messages), 1)                     AS "сообщений на человека",
       round(avg(cta_shown), 2)                    AS "показов оффера"
FROM funnel_users
WHERE bucket <> '' GROUP BY bucket;
```

### Доходимость курса

```sql
SELECT course, max(step) AS дошли_до, count(*) AS людей
FROM funnel_users WHERE course <> '' GROUP BY course, step ORDER BY course, step;
```

Курс — причина вернуться завтра. Если люди сыпятся на втором шаге, проблема не
в цене.

### Догоняющие сообщения

```sql
SELECT payload->>'step' AS шаг, count(*) AS отправлено
FROM funnel_events WHERE event = 'followup_sent' GROUP BY 1 ORDER BY 1;
```

Смотреть вместе с `followup_blocked`: много блокировок означает, что цепочка
бьёт в стену, а не что люди не отвечают.

### Границы бота

```sql
SELECT count(*) FROM funnel_events WHERE event = 'price_talk_blocked';
```

Не метрика роста, а метрика доверия. Каждое срабатывание — случай, когда модель
полезла говорить о деньгах и её остановили. Растёт — надо править промпт, а не
радоваться, что защита работает.

## 3. Сколько нужно людей, чтобы вывод был выводом

Это то место, где тесты обычно и ломаются: сравнение делают на сотне человек,
получают «B лучше на 40%» и перестраивают по этому продукт.

Формула для сравнения двух долей (80% мощность, 95% уверенность):

```
n на группу ≈ 7,84 × (p₁(1−p₁) + p₂(1−p₂)) / (p₁−p₂)²
```

| Что сравниваем | Ожидаемая база | Хотим увидеть | Нужно на группу | Итого |
| --- | --- | --- | --- | --- |
| Покупку | 2% | 3% | **≈ 3 800** | ≈ 7 600 |
| Клик по офферу после подарка | 30% | 36% | **≈ 960** | ≈ 1 920 |
| Начало курса после приветствия | 40% | 48% | **≈ 600** | ≈ 1 200 |

**Отсюда правило теста:** на покупке A/B не ставим — её просто считаем
накопительно. Сравниваем середину воронки, где доли большие и разница видна на
тысяче человек, а не на восьми.

Базовые доли в таблице — предположение, а не замер: до первого трафика их никто
не знает. Первый прогон нужен именно чтобы их узнать, и после него таблицу надо
пересчитать теми же формулами.

## 4. Что считается провалом

Это решения, а не нормы отрасли. Числа выбраны так, чтобы по ним можно было
остановиться, а не чтобы они выглядели красиво.

| Условие | Что это значит | Что делаем |
| --- | --- | --- |
| Меньше 60% взяли подарок | Приветствие не доносит, что подарок бесплатный | Правим первое сообщение, не трогая рекламу |
| Меньше 25% дошли до оффера | Разговор не доводит до предложения | Смотрим, на каком шаге курса сыпятся |
| Оффер видели, ни одной оплаты на 300 человек | Цена или доверие | Не снижаем цену первым делом — сначала смотрим `price_talk_blocked` и отзывы |
| Стоимость `start` выше 2 долларов | Объявление или канал | Меняем объявление, канал не меняем до трёх попыток |
| `price_talk_blocked` чаще, чем у 5% людей | Модель лезет в цены | Правим промпт: это не защита сработала, это промпт течёт |

Красная линия одна: **остановить тест, если за первые 100 человек не было ни
одного `gift_sent`**. Это означает техническую поломку, а не плохую рекламу, и
жечь бюджет дальше незачем.

## 5. Какие гипотезы стоит проверить

В порядке дешевизны. Первые две не требуют ни строчки кода — только текст.

1. **Приветствие по направлению против общего.** Деление `bucket` уже есть,
   метка направления уже доезжает. Проверяем, добавляет ли приветствие «про сон»
   доходимость до курса против общего списка всех шести тем.
2. **Подарок до разговора против подарка после первого ответа.** Сейчас отдаётся
   сразу. Гипотеза: отданный после первого содержательного ответа ценится выше и
   даёт больше дошедших до оффера.
3. **Оффер в три шага против двух.** Сейчас три: условия → состав и цены → счёт.
   Проверяем, не теряем ли мы людей на лишнем шаге.
4. **Курс как вход против разговора как входа.** Кнопка «начать курс» первым
   экраном против «спроси меня о чём угодно».

Чего проверять не надо, потому что ответ уже известен из решений заказчика:
скидки (сняты 03.09), украинская версия (не будет), ступени тарифа (три,
$10 / $20 / $100).

## 6. Чего не хватает

| Нужно | От кого | Без этого |
| --- | --- | --- |
| Идентификатор GTM | заказчик | нет аналитики сайта, только бот |
| Бюджет на Telegram Ads и модерация | заказчик | тест не запускается |
| Решение по 21 украинскому ролику | заказчик | часть библиотеки нельзя отдавать |
| Первый замер базовых долей | трафик | таблица в разделе 3 остаётся предположением |

Сквозной аналитики «показ рекламы → оплата» не будет в принципе: Telegram Ads не
отдаёт идентификатор показа. Максимум, что связывается, — метка кампании в
ссылке и всё, что человек сделал дальше. Этого достаточно, чтобы сравнивать
кампании между собой, и недостаточно, чтобы считать окупаемость одного
объявления.
